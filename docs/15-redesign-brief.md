## 0. このサービスは何か

京都産業大学の課外活動団体 約158件を、**同じ項目で横断して比べられる**ようにする学生向けサイト。運営は1人（大学1年・個人事業主）。

- 大学公式には団体名と区分しか載っていない。新入生が知りたい「何曜日にやってるか／年会費いくらか／何人いるか／男女比／掛け持ちできるか／今から入れるか」が存在しない
- 新入生はInstagramを1団体ずつ開いて調べるしかなく、**横断比較の手段がない**
- 解き方は「団体に入力してもらう」ではなく、**運営が全団体に聞き取って同じ項目を埋める**。入力の手間をこちらが全部引き受けることがサービスの本体であり、営業上の最大の武器
- 「一番いい団体を薦める」のではなく「**失敗しない団体を自分で選べる**」ようにする。新入生が実際にやっているのは最良の選択ではなく地雷の回避なので、そこに合わせる

### 意図的にやらないと決めていること

おすすめ・ランキング・スコアリング／口コミ・レビュー・評価点／診断マッチング。
理由：**運営が団体を序列化することになる。**大学の中で中立に運用できなくなり、団体との関係が壊れる。名鑑は台帳であってメディアではない。

### 利用者は2種類いて、優先順位が逆転している

| | 新入生（主たる読者） | サークル代表（第一の相手） |
|---|---|---|
| 時期 | 3月末〜5月、次いで9月 | **いま、まさに毎日** |
| 場面 | スマホ縦画面で3分。絞り込みと比較 | 面談中に、こちらのスマホを**30秒**覗き込む |
| 判断すること | どこに入るか | これは本物か／うちが載るとどう見えるか／面倒なことをさせられないか |

**公開前に画面を見せて掲載同意を得るのが実際の運用フロー**なので、いまはUIの完成度がそのまま営業成績になる。ただしサイトの最終的な読者は新入生。**この2つの要求が衝突する箇所が、今回の作り直しの中心。**

## 1. 現状（2026年9月6日時点）

### 1-1. 技術構成とデータの流れ

```
Googleフォーム（面談中に運営が自分で入力。団体には見せない）
   ↓
スプレッドシート  1行 = 1団体   ← 掲載データの唯一の原本
   ↓ npm run sync（決定的なスクリプト。AIを使わない）
data/circles.json ＋ public/photos（3:2クロップ・WebP・幅1200と600）
   ↓ git push
Vercel が自動でビルド・公開
```

- Next.js 16（App Router）／ TypeScript ／ Vercel、**完全な静的生成**。SSR・ISR・APIルートなし。サーバーもDBも持たない
- 費用はドメイン代（年1,500円程度）のみ
- 構成を変えるのは団体数が増えたときではなく、**団体自身に編集させ始めるとき**（そのときSupabaseへ）
- 写真は `next/image` の最適化を使わない（sync が変換済みのものを置く）

### 1-2. 実装済みの画面

| パス | 中身 | 状態 |
|---|---|---|
| `/` | 一覧（S-01）。大きさの違うタイル（S/M/L）を混ぜて並べる | 実装済み |
| `/c/[id]` | 団体ページ（S-02）。`c001` 形式 | 実装済み |
| 表紙（S-00） | 要件定義では独立した画面。実装では一覧の中のシートとして同居 | **独立ルートは存在しない** |

一覧の絞り込み：**活動曜日（複数）／区分／ジャンル／年会費（0円・〜3,000・〜10,000・10,000〜）／初心者／掛け持ち可**。絞り込み結果はURLに載る（`?days=0,3&cats=...`）。DMに貼って共有できることが要件。検索窓は「158件なら絞り込みで足りる」として作っていない。

団体ページの演出：
- 全画面（100dvh）の写真から始まり、ゆっくりズームイン
- 一覧のカードを押すと、その写真が拡大して全画面になる（View Transitions）
- スクロールすると写真が背後に沈み、詳細シートが下から立ち上がる
- 写真は最大8枚。5秒ごとに自動クロスフェード、手動スワイプ可。**触ったら自動送りは止めて再開しない**
- 写真がない団体はジャンル色のベタ塗りに団体名を大きく組む。「No Image」「準備中」とは書かない

配色：地 `#EFEFEB` ／ 文字 `#14213A` ／ **山吹 `#E8A33D` は「一致」にしか使わない**（一覧で選んだ曜日と活動日が一致したときだけ。ボタン・リンク・ロゴ・装飾に使わない）。

### 1-3. 掲載項目（14。増やさないと決めている）

キャッチコピー／区分（大分類＋公式の所属区分）／活動日／活動時間・活動場所／掛け持ち可否／年会費／年会費以外にかかる金／所属人数／初心者の数／男女比／この団体について（紹介文3〜5行）／代表からの一言／いま入れるか／いつ聞いた情報か

**載せないと決めたもの**：歴史・実績・OB・顧問（大学公式にある）／SNSフォロワー数（団体間の格差が出る）／**個人名と顔写真**（掲載同意の範囲が変わる。団体紹介が人物紹介になる）／口コミ・評価。
→ 面談で「これも載せて」と言われたときに**断る根拠**として使っている。

### 1-4. データ型（抜粋。フィールド名は snake_case）

```
id, short_name, name, division, category, genre, one_liner,
active_days: number[]                       // 0=月…6=日。空配列は「活動日 未確認」
active_times: Record<string,[string,string]>// 曜日ごとの開始終了
frequency_per_week, hours_per_session, place,
annual_fee: number | null                   // 0=無料、null=未確認。絶対に混同しない
extra_cost_note: string | null              // "なし"=確認済みで無い、null=聞けていない
member_count, beginner_count, first_year_count,
gender: {male,female} | null                // 実数で保持。表示時に合計10へ丸める。片方欠けたら null
multi_club_ok: string | null                // 条件つきは条件文をそのまま入れる。booleanにしない
description, leader_comment:{text,role},     // role は「代表（3年）」。個人名を入れない
recruiting, next_recruit:{date,what},
surveyed_at: "2026-09", sns:{instagram,x,website},
photos: string[]                            // 0〜8枚。1枚目が一覧とOGPに出る
tile_size: "S"|"M"|"L"                      // 一覧のタイルの大きさ。シートで手で決める
```

**未確認の扱いが設計の中心**：聞けなかった項目を空欄にしない。数字カードの中は `—`、それ以外は文字で `未確認` と出す。**カードや行ごと消して詰めない。**未確認の量がそのまま「まだ聞けていない量」として見えるのが正しい状態。面談中に「ここを埋めさせてください」と言える。

### 1-5. 面談フォームの現状

**団体に送るフォームではない。**面談中〜直後に、運営が自分のスマホで埋める。営業で「団体側に入力作業は発生しません」と言っているのが武器なので、ここは崩さない。写真だけはDMで受け取る。

現行は **10セクション・40問**。管理(4) → 基本情報(5) → 活動(4) → 人数(4) → お金(3) → 入部条件(5) → 文章(4) → SNS(3) → 写真(5) → 掲載確認(3)。設問の順序は面談スクリプトと同じ。

聞けなかった項目は空欄のまま送信（＝未確認）。例外は年会費0円で、これは `0` と入力する。

面談後にシート側で手で埋める列：`紹介文`／`キャッチコピー`／`写真URL`／`除外理由`／`最終更新日`／`tile_size`。
`公開してよいか = OK` の行だけを sync が機械的にビルドに含める。

### 1-6. 実データの状態 ★ここが重要

**シートに入っているのは3団体だけ**（c054・c056・c058）。写真14枚。一般公開の条件は「掲載OK 30件以上／主要4区分が全部1件以上／全団体で活動日が埋まっている」なので、**まだ公開していない**（`noindex`）。

直近の sync が出した警告：

```
c054  ジャンルが不正（"運動"）→ その他
c054  活動時間の形式が HH:MM-HH:MM でない（"春学期は月水木　毎学期決めている　週３回"）
c054  活動曜日にチェックがあるが活動時間が空
c054  キャッチコピーが34文字（20文字超）
c056  活動時間の形式が HH:MM-HH:MM でない（"月１回　不定"）
```

さらに実データを見ると、`multi_club_ok`（掛け持ちの可否）に **「少ない　一筋多め」** という、可否ではない答えが入っている。`active_times` は3団体とも空。`gender` は3団体とも `null`（男女どちらかが空欄）。

つまり **3団体しか入れていない段階で、自由記述の設問がほぼ全部データを壊している。**

### 1-7. すでに決まっているが、まだコードにもドキュメントにも反映されていない変更

ここが今いちばん散らかっている。**整合を取ること自体が今回の作業に含まれる。**

1. **9/2に、Apps Scriptで新しいフォームとスプレッドシート（`団体マスタ` / `回答` / `掲載データ` の3タブ）を作った。**リポジトリ側のドキュメントと sync スクリプトは、旧・単一シート40問の前提のまま
2. 写真を「**アイコン写真**」と「**その他の写真**」に分けて持つと決めた。型は `photos: string[]` のままで、一覧サムネ・OGP・全画面ヒーローが全部 `photos[0]` を共用している
3. フォームから外すと決めた項目：**1回あたりの時間／年会費以外の費用／お酒の場の回数／新入生からよく聞かれる質問／次に人を入れる時期**。型（`hours_per_session`・`extra_cost_note`）にもUI（「年会費以外にかかる金」は現行UIで重要項目扱い）にも残っている
4. 掲載データは「京産大限定」で作ると決定済み（全国区の競合と正面衝突しない粒度）

### 1-8. まだ決まっていないこと

サイト名とドメイン（面談で口頭に出るので早く要る）／公開時期（4月新歓に合わせるか、後期の夏新歓と同時か）／収益の仮説（サークルは払わない。誰が払うのか）／翌年の更新責任者／届出団体54を体育会より先に回るか。

## 2. 崩してはいけない原則

作り直しの提案が下のどれかを崩すなら、**崩すこと自体を論点として明示**してから提案する。黙って前提を変えない。

1. 団体に入力の手間をかけさせない。「団体側に入力してもらう」案は却下
2. 未確認を隠さない。空欄より「未確認」の表示を選ぶ。`¥0`（無料）と `—`（未確認）を絶対に混同しない
3. 序列化しない。おすすめ・評価・ランキング・診断は作らない
4. 掲載項目を増やさない。足したくなったら**代わりに何を消すか**を必ずセットで出す
5. 個人名と顔写真を出さない
6. 静的生成のまま（サーバー・DBを持たない）
7. **面談が止まる作業をしない。**先回りの実装より、次の団体に会うほうが優先
8. 運営は1人。158団体を1人で回せない設計は失格
9. スマホ縦画面（375〜430px）が基準。タップ領域44px以上、`prefers-reduced-motion` 対応

## 3. 作り直したい理由（分かっている問題）

**これは仮説であって確定した問題リストではない。**検証し、足りないものを足し、優先順位をつけてほしい。

### A. サイトのUI

- 面談で代表に30秒見せる用途と、新入生が3分かけて絞り込む用途が、**同じ画面に同居している**。いまは前者しか実戦投入されていない
- 3団体しか入っていない状態で代表に見せると「未確認だらけ」「スカスカ」に見える。**未確認を隠さない原則と、営業で信用を得たい要求が正面から衝突している**
- 表紙（S-00）が独立していない。初見の新入生がどこから入って何を理解して一覧に進むのかが未定義
- 158件をタイル混在レイアウトで並べたときの一覧性・スクロール量が、3件では検証できていない
- **横断比較が価値の中核なのに、比べる導線が「戻ってもう1つ開く」しかない**（ランキングはNGだが、比較そのものはNGではない）
- 一覧→詳細→戻るで、絞り込み状態とスクロール位置がどう戻るべきかが決まっていない
- 掲載前プレビュー（`noindex`・「これは掲載前の確認用です」の明示）を、どの画面のどこに出すか

### B. 面談フォームの導線

- **5分の面談に対して40問**。実測で何分かかるか計測していない
- 自由記述の設問が sync を壊している（活動時間・ジャンル・掛け持ち）。3団体中2団体で警告、1団体は掛け持ち欄に無関係な答えが入った
- 面談時点で埋まらない項目（掲載確認3問・紹介文・キャッチコピー・写真URL・tile_size）がフォームとシートに分散していて、**1団体ごとに「どこまで終わったか」が見えない**
- 写真の受け取りがDM→Drive→シートに手貼り。フォームのファイルアップロード設問と経路が二重になっている
- 掲載確認（プレビューURLを送る→OKをもらう）の往復が団体ごとに発生する。追跡手段がシートの列だけ
- 9/2の新フォーム（3タブ）と、旧40問前提のドキュメント・sync が食い違ったまま

### C. データ構造

- `photos: string[]` のままで、アイコン／ヒーロー／OGP を分けられない
- 外すと決めた項目が型・UI・フォームに残っている。消すなら「14項目」の定義とUI仕様のどこを直すか
- `active_times`（曜日ごとの時間）は型として存在するが、実データは0件。**この形を維持するのか、曜日ごとの時間を諦めるのか**
- `gender` は片方欠けたら null。3団体とも埋まっていない。聞き方の問題か、項目の問題か
- `tile_size` を1件ずつ手で決める運用が158件でスケールするか
- 団体マスタ（c001〜c158の採番と営業の進捗）と、掲載データ（公開する中身）が同じ台帳に混ざっている

## 4. 出してほしいもの

この6つ。**上から順に、1つずつ。**

1. **問題の再整理** — §3の仮説を検証して、消すもの・足すもの・優先順位を出す。「いま直さないと営業が止まるもの」と「公開までに直せばいいもの」を分ける
2. **画面と状態の一覧** — 画面ごとに、出す情報・遷移・URL。**状態を落とさない**こと（未確認だらけの団体／写真ゼロの団体／絞り込み0件／掲載前プレビュー／158件中5件しかない時期）
3. **面談1本の導線** — アポ→面談→写真受領→紹介文作成→掲載確認→公開 までを**分単位**で。各ステップで「どこがフォームで、どこがシートで、どこが自動か」「1団体あたり何分か」を明示
4. **フォーム設問の再設計** — 何問に減らすか、各設問の形式（自由記述にしていい設問の基準を先に定義する）、順番、必須の基準。**外すと決めた5項目の扱いを含める**
5. **データ構造の変更差分** — 追加／削除／型変更を表で。それぞれ「影響するUIの箇所」と「シートの列の変化」をセットで
6. **未決の論点** — あなたが決められないもの。**質問は最後にまとめて、5個以内。**多く出すより、答えが出れば設計が動くものを選ぶ

## 5. 書き方

- 見出し付きMarkdown。表を使っていい。**コードは書かない**
- 提案には毎回「なぜそうするか」と「**代わりに何を捨てるか**」を書く
- 断定できないことを断定しない。分からないところは「未確認」と書く。このプロジェクト自身のルールと同じ
- 一般論のUIベストプラクティスを並べない。**158団体・1人運用・面談で見せる**という条件に固有の話だけ書く
- 日本語。長さは必要なだけ。ただし §4 の1つ目から順に、確認しながら進める

# 京産大サークル名鑑 要件定義書 v2.0

作成: 2026/08/30 ／ 東田蒼人
対象: 京都産業大学の課外活動団体をまとめた学生向け情報サイト
このファイルの位置づけ: **何を作り、何を作らないかの判断基準。**迷ったらここに戻る。

---

## 1. 背景

京都産業大学には約158の課外活動団体がある。大学公式サイトには団体名と区分の一覧はあるが、**新入生が入るかどうかを決めるのに必要な情報が載っていない。**

具体的に欠けているのは次の5つ。

- 何曜日の何時に活動しているか
- 年会費が実際いくらか（年会費以外の出費を含めて）
- 何人いるか、そのうち初心者から始めた人が何人か
- 男女比
- 掛け持ちできるか、いまから入れるか

新入生はこれらを、団体ごとのInstagramを1つずつ開いて調べるか、新歓の現場で口頭で聞くしかない。**横断して比べる手段が存在しない。**

団体側も困っている。Instagramの運用は代表の交代で途切れ、過去の投稿は流れて見えなくなる。新歓期以外に発見される経路がない。

---

## 2. このサービスが解くこと

**158団体を、同じ項目で、横断して比べられる状態にする。**

「一番いい団体」を推薦するのではない。**「失敗しない団体」を自分で選べるようにする。**新入生が実際にやっているのは最良の選択ではなく、地雷の回避なので、そこに合わせる。

### 2-1. 中核となる価値

**運営が全団体に聞き取って、同じ項目で埋める。**これが他のどの手段とも違う点。

団体に入力してもらう形にすると、熱心な団体だけが埋まって、比較にならない。**入力の手間をこちらが全部引き受けることが、サービスの本体**であり、営業上の最大の武器でもある。

### 2-2. 意図的にやらないこと

- おすすめ・ランキング・スコアリング
- 口コミ・レビュー・評価点
- マッチング（診断して団体を提示する）

いずれも**運営が団体を序列化することになる。**大学の中で中立に運用できなくなるし、団体との関係が壊れる。名鑑は台帳であって、メディアではない。

---

## 3. 利用者

### 3-1. 新入生（主たる読者）

- 時期: 3月末〜5月、次いで9月
- 経路: InstagramのDMやストーリーからのリンク流入が中心。検索流入は少ない
- 端末: **ほぼスマホ縦画面**
- 滞在: 3分程度。目的は絞り込みと比較

### 3-2. サークル代表（第一の相手）

- 場面: 面談中に、こちらのスマホを30秒覗き込む
- 判断すること: これは本物か／うちの団体が載るとどう見えるか／面倒なことをさせられないか
- **公開前に画面を見せて掲載の同意を得る**のが実際の運用フローなので、UIの完成度がそのまま営業成績になる

### 3-3. 運営（自分）

- 面談・入力・写真の受け取り・確認依頼・公開まで全部やる
- **1人で158団体を回せる運用設計が必須要件**

## 4. スコープ

### 4-1. v1で作るもの

| 画面 | 内容 |
|---|---|
| 一覧（S-01） | 158団体を並べ、曜日・区分・掛け持ち可否で絞り込む |
| 団体ページ（S-02） | 1団体の全情報。全画面写真＋スクロールで詳細 |
| 表紙（S-00） | サイトの説明と一覧への導線 |

### 4-2. v1で作らないもの

- ログイン・会員機能
- 団体自身による編集
- 「気になる」の端末をまたいだ保存
- 検索窓（158件なら絞り込みで足りる）
- 通知
- アプリ（ネイティブ）

### 4-3. 将来やるかもしれないこと

- 団体自身による情報更新（**構成をSupabaseへ移す分岐点**）
- 新歓イベントのカレンダー
- 夏新歓フェスとの連動

## 5. 掲載項目（確定）

団体ページに出す情報は次の15。**増やさない。**

1. キャッチコピー
2. 区分（大分類＋公式の所属区分）
3. 活動日
4. 活動頻度・活動場所
5. 掛け持ちの状況
6. 参加の緩さ
7. 先輩の呼び方
8. 年会費
9. 所属人数
10. 初心者の数
11. 男女比（合計10の比率で表示。データは男子の割合（%）で保持）
12. この団体について（紹介文3〜5行）
13. 代表からの一言
14. いま入れるかどうか
15. いつ聞いた情報か

### 5-1. 載せないと決めたもの

| 項目 | 理由 |
|---|---|
| 歴史・実績・OB・顧問 | 大学公式にあり、新入生の判断材料にならない |
| SNSのフォロワー数 | 団体間の格差がそのまま出る |
| 個人名・顔写真 | 掲載同意の範囲が変わる。団体紹介が人物紹介になる |
| 口コミ・評価 | §2-2 |

**面談で「これも載せてほしい」と言われたときに断る根拠として使う。**団体ごとに載っている項目が違う名鑑にしない。

### 5-2. 未確認の扱い ★設計の中心

聞けなかった項目を空欄にしない。**必ず「未確認」と分かる形で出す。**（数字カードの中は `—`、それ以外は文字で `未確認`）

- 未確認の量が、そのまま「まだ聞けていない量」として見える状態が正しい
- 面談中に「ここを埋めさせてください」と言える
- **`¥0`（無料）と `未確認` を必ず区別する。**年会費を無表示にすると無料に見える

## 6. 機能要件

### 6-1. 一覧（S-01）

- 158団体をカードで一覧表示
- 絞り込み: 活動曜日（複数選択）／区分／ジャンル／掛け持ち可否
- 絞り込み結果はURLに反映する（**共有できること。**「月曜空いてる人はここ」でDMに貼れる）
- 選んだ曜日と一致した団体は、一致した曜日を山吹で示す

### 6-2. 団体ページ（S-02）

- 全画面（100dvh）の写真から始まり、ゆっくりズームイン
- 一覧のカードを押すと、その写真が拡大して全画面になる（View Transitions）
- スクロールすると写真が背後に沈み、詳細のシートが下から立ち上がる
- 写真は最大8枚。5秒ごとに自動でクロスフェード、手動スワイプ可。**触ったら自動送りは止めて再開しない**
- 写真がない団体はジャンル色のベタ塗りに団体名を大きく組む。**欠落に見せない**

### 6-3. 掲載前プレビュー

- 公開していない団体を、団体に見せるためのURLが存在すること
- **検索に載らないこと**（`noindex` 必須）
- 「これは掲載前の確認用です」と画面上に明示すること

## 7. 非機能要件

| 項目 | 基準 |
|---|---|
| 対応端末 | スマホ縦画面が基準（375〜430px）。PCは中央1カラム |
| 表示速度 | 静的生成。Lighthouse パフォーマンス90以上 |
| アクセシビリティ | タップ領域44px以上／フォーカス可視／`prefers-reduced-motion` 対応／自動で動く要素に一時停止手段 |
| 可用性 | サーバーを持たない。落ちる箇所を作らない |
| 費用 | ドメイン代（年1,500円程度）のみ。ホスティングは無料枠内 |
| 運用 | データ更新から公開まで1コマンド＋1コミット |

## 8. 技術構成

**Next.js（App Router）＋ Vercel の静的生成。**サーバーもデータベースも持たない。

```
Googleフォーム（運営が面談中に入力）
   ↓
スプレッドシート  1行 = 1団体   ← 掲載データの唯一の原本
   ↓ npm run sync（決定的なスクリプト。AIを使わない）
circles.json ＋ 最適化済み画像
   ↓ git push
Vercel が自動でビルド・公開
```

- **原本はスプレッドシート。**`circles.json` は中間生成物。手で直さない
- 写真はDriveから取得して3:2クロップ・WebP化・EXIF削除してリポジトリに置く
- `公開してよいか = OK` の団体だけをビルドに含める。**人間の記憶で管理しない**

### 8-1. 構成を変える条件

団体数では変えない。500団体でも静的生成で足りる。**変えるのは団体自身に編集させ始めるとき**（Supabaseへ）。そのときも `circles.json` の形は変えず、画面には手を入れない。

### 8-2. 採用しないもの

| 技術 | 理由 |
|---|---|
| WordPress | 記事ではなく構造化データを扱う。サーバーとDBと保守が増える |
| CMS全般 | 編集者が1人しかいない。シートで足りる |
| データベース | 158件・年1回更新・書き込み1人。ビルド時に読むほうが速く安く壊れない |

---

## 9. 運用フロー

1. 大学公式の一覧から団体IDを `c001`〜`c158` で採番（**一度振ったら変えない**）
2. 団体にDMまたは対面でアポを取る
3. 面談でフォームを埋める（1団体5分）
4. 写真を3〜5枚DMで受け取り、Driveへ
5. 聞き取りメモから紹介文を書く
6. プレビューURLを送って掲載確認
7. OKが出たらシートを更新 → `npm run sync` → コミット → 公開
8. 翌年、同じ団体に更新の聞き取り（**取材時期をサイトに出しているので、根拠になる**）

---

## 10. 公開の条件

次を満たすまで一般公開しない。

1. 掲載OKが出た団体が**30件以上**（少なすぎると「使えないサイト」の印象が固定する）
2. 主要4区分（体育会・文団連・届出団体・学生プロジェクト）が**すべて1件以上含まれる**
3. 全団体で活動日が埋まっている（**絞り込みの中核なので、ここが未確認だらけだと機能が死ぬ**）
4. 掲載前確認のプロセスを経ていない団体が1件も含まれていない

---

## 11. リスクと対応

| リスク | 対応 |
|---|---|
| 情報が古くなる | 取材時期を全ページに表示。年1回の更新を運用に組み込む |
| 大学から問い合わせが来る | 公式・非公式の関係を明示。全団体に事前確認を取っている記録を残す |
| 掲載を断られる | 断られた団体は載せない。`公開してよいか` で機械的に除外 |
| 写真の権利・肖像 | 提供元と掲載可否と顔出しNGの有無をデータとして記録する |
| 1人で回らない | 面談は1団体5分。入力はフォーム。変換と公開は自動化済み |
| 誤情報の掲載 | 公開前に必ず団体本人の確認を取る。修正・取り下げの導線を全ページに置く |

---

## 12. まだ決まっていないこと

1. サイト名とドメイン（**面談で口頭に出るので早めに要る**）
2. 公開時期（4月新歓に合わせるか、後期の夏新歓と同時か）
3. 収益の仮説 — サークルは払わない。誰が払う想定か
4. 翌年の更新責任を誰が持つか
5. 届出団体54を体育会より先に回るか

---

## 13. 判断の原則

迷ったときはこの順で決める。

1. **団体に手間をかけさせない。**入力させる案は却下する
2. **未確認を隠さない。**空欄より「未確認」の表示を選ぶ
3. **序列化しない。**おすすめ・評価・ランキングは作らない
4. **面談が止まる作業をしない。**先回りの実装より、次の団体に会う
5. **項目を増やさない。**足したくなったら、代わりに何を消すか考える
